# M12 阶段调试日志导致 DLL 未更新

> 日期：2026-09-02  
> 类型：构建流程问题  
> 严重度：中（症状严重但根因简单）  
> 状态：已解决

## 问题描述

**症状**：
- 用户报告"右侧留白总会比左侧多"（窗口 434px，右侧留白 54px vs 左侧 20px）
- M12 必修 1-3 + M12-v2 + M12-v3 全部实施并通过测试（407 tests pass）
- 用户运行 `flutter run` 后问题依然存在
- 添加调试日志后重新编译，问题神奇地消失了

**调试过程关键发现**：
1. M12-v3 怀疑 epsilon 扣除导致断行提前（假设错误）
2. M12-v4 添加调试日志输出 `max_width` 参数
3. 调试日志显示 `max_width=289.0`（期望 394px = 434 - 20 - 20）
4. 添加调试日志并重新编译后，**问题消失**

## 根本原因

**不是代码逻辑错误，而是 DLL 文件没有被正确更新到运行时位置。**

### 原因分析

1. **Rust 编译输出路径**：
   - `cargo build --release` 输出到 `rust/target/release/bridge.dll`

2. **Flutter 运行时加载路径**：
   - Flutter 从 `rust/crates/bridge/target/release/bridge.dll` 加载

3. **路径不一致导致**：
   - 修改 Rust 代码后直接 `cargo build --release`
   - 新 DLL 生成到 `rust/target/release/bridge.dll`
   - 但 Flutter 仍加载旧的 `rust/crates/bridge/target/release/bridge.dll`
   - **用户看到的是旧版本的行为**

4. **为什么添加调试日志后问题消失**：
   - 添加调试日志后重新运行了 `fix_sync.ps1`（或手动复制了 DLL）
   - `fix_sync.ps1` 正确执行了 DLL 复制步骤
   - Flutter 加载到了**包含所有 M12 修复的新 DLL**
   - 问题实际上在 M12 必修 1-3 就已经修复，只是 DLL 没更新

## 解决方案

### 正确的构建流程

**始终使用 `fix_sync.ps1` 脚本**（而非直接 `cargo build`）：

```powershell
cd D:\android\example\legado_flutter
.\fix_sync.ps1
```

该脚本执行完整流程：
1. 清理 Flutter 缓存
2. 清理 Rust 缓存
3. 获取 Flutter 依赖
4. 重新生成 FFI 绑定（`flutter_rust_bridge_codegen generate`）
5. **编译 Rust 代码**（`cargo build --release`）
6. **复制 DLL 到正确位置**（`rust/target/release/bridge.dll` → `rust/crates/bridge/target/release/bridge.dll`）
7. 构建 Windows 应用

### 如果只想快速测试 Rust 修改

```powershell
# 1. 编译 Rust
cd D:\android\example\legado_flutter\rust
cargo build --release

# 2. 复制 DLL（关键步骤！）
Copy-Item "target/release/bridge.dll" -Destination "crates/bridge/target/release/bridge.dll" -Force

# 3. 运行 Flutter
cd ..
flutter run -d windows
```

**第 2 步（复制 DLL）是必须的，不能省略！**

## 预防措施

### 1. 文档化构建流程

已在 `docs/AGENTS.md` 和 `README.md` 中明确说明：
- ✅ **正确**：使用 `fix_sync.ps1`
- ❌ **错误**：直接 `cargo build --release`（会导致 DLL 不更新）

### 2. 添加构建验证

可选：在 `fix_sync.ps1` 中添加 DLL 哈希校验，确保两个位置的 DLL 一致：

```powershell
$sourceHash = (Get-FileHash "rust\target\release\bridge.dll").Hash
$targetHash = (Get-FileHash "rust\crates\bridge\target\release\bridge.dll").Hash
if ($sourceHash -ne $targetHash) {
    Write-Host "❌ 警告：DLL 哈希不一致，可能存在版本错位" -ForegroundColor Red
    exit 1
}
```

### 3. CI/CD 流程

如果引入 CI/CD，必须包含 DLL 复制步骤：

```yaml
- name: Build Rust
  run: cargo build --release --manifest-path rust/Cargo.toml

- name: Copy DLL to Flutter load path
  run: |
    Copy-Item rust/target/release/bridge.dll `
      -Destination rust/crates/bridge/target/release/bridge.dll `
      -Force
```

## 教训总结

1. **FFI 项目的 artifact 路径陷阱**：
   - 编译输出路径 ≠ 运行时加载路径
   - 必须有显式的复制/链接步骤
   - 直接编译看似成功，实际运行的是旧代码

2. **调试日志的副作用**：
   - 添加调试日志本身不修复问题
   - 但调试日志触发了"完整重新构建" → DLL 被正确复制
   - **问题消失的真正原因是构建流程完整执行**

3. **症状与根因的误导**：
   - 症状："右侧留白多" → 怀疑排版算法错误
   - 实际根因：旧 DLL 还没有包含修复代码
   - **先验证运行的代码版本，再调试算法逻辑**

4. **M12 修复是有效的**：
   - M12 必修 1（font_size 参数）✅
   - M12 必修 2（feedPageTextsWithPrefixes）✅
   - M12 必修 3（cache miss fallback）✅
   - M12-v2（字符边界对齐）✅
   - **这些修复从一开始就是正确的**，只是 DLL 没更新到运行时
