# 修复记录：CRLF 字节偏移漂移与净化后行号失效

## 测试发现

对真实书籍《贷款武圣(1-280章).txt》（5.2MB，CRLF 行尾，279 章）做端到端验证时，
发现章节边界存在系统性错位，暴露出两个此前未识别的根本原因：

### 根因 1：CRLF 文件上的字节偏移累积漂移（最关键）

**位置**：`chapter_extractor.rs::build_chapter_info()`、`txt_parser.rs::LineOffsetMapper::build()`、
`calculate_line_number()`

**问题**：原代码用 `content.lines()[i].len() + 1` 累加字节偏移。
Rust 的 `lines()` 会剥掉行尾的 `\r`，因此 CRLF 文件每行实际占 `len + 2` 字节，
累加时每行少算 1 字节。

**后果**：第 N 行之前有 N 行 → 偏移少算 N 字节，逐行累积。
279 章的书籍越往后漂移越大，再经字符边界"向前对齐"后落到某行中间，
导致章节内容开头出现上一章结尾、重复标题甚至标题被截断（如"身"/"大周朝。"）。
这正是用户最初截图问题的真正根源。

**修复**：改用原始字节扫描 `\n` 构建行起始偏移表，对 LF / CRLF 均精确：

```rust
let mut line_starts = vec![0];
for (i, b) in content.bytes().enumerate() {
    if b == b'\n' { line_starts.push(i + 1); }
}
// 章节起始 = 标题行的下一行行首；结束 = 下一章标题行行首
```

三处统一修复：
- `build_chapter_info()`：一次性构建 `line_starts` 表（同时消除原先 O(章节数×总行数) 的重复累加）
- `LineOffsetMapper::build()`
- `calculate_line_number()`

### 根因 2：净化重构行结构后，原始行号全部失效

**位置**：`txt_parser.rs::build_cleaned_chapter_cache()`

**问题**：`ContentCleaner` 的智能分段会合并续行、增删空行，
净化后的行结构与原始内容完全不同。
旧逻辑却用**原始内容**上计算的 `chapter_metadata.line_number`
去映射**净化后**的内容，边界必然错位。

**修复**：在净化后的文本上**重新运行 JS 引擎章节识别**
（与导入时同一套规则，保证章节数一致）；
若数量不一致或识别失败，回退为按标题在净化文本中单调顺序对齐。

## 说明

- 章节内容现在从正文第一行开始，重复标题不再进入缓存内容；
  `reader_core::remove_duplicate_title()` 保留作为 EPUB 等其他流程的安全网。
- `bridge/api.rs` 当前未给 TXT parser 设置 ContentCleaner（cleaner=None），
  净化缓存路径与验证脚本行为一致；后续如启用净化器，
  新架构会在净化后文本上重新识别章节，无需额外改动。
- `book_source_engine` 的 7 个 doc-test 失败为预先存在的问题
  （文档示例缺少类型导入），与本次修改无关。
