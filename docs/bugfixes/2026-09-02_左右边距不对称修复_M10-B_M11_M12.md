# 左右边距不对称修复 (M10-B/M11/M12)

> 日期：2026-09-02  
> 类型：排版精度问题  
> 严重度：高（视觉体验严重影响）  
> 状态：已解决

## 问题描述

**症状**：
- 阅读页右侧留白总会比左侧多（例如：窗口 434px，左侧 20px vs 右侧 54px）
- TXT 和 EPUB 类型书籍均存在此问题
- 段落越多越明显，非段落缩进问题
- 无首行缩进的正常行仍然右侧留白过大

**用户反馈**：
```
"右侧边距要比左侧多很多"
"这个问题不止在 txt 文档下出现，epub 类型文件也是如此"
"即便是在段落比较多的情况下，这个问题也会出现"
```

**实测数据**（窗口 434px，左右边距各 20px）：
- 期望 `max_width` = 434 - 20 - 20 = 394px
- 期望 `rightEdge` ≈ 414px（394 + 20）
- **实际观察**：部分段落 `rightEdge` = 360-380px，右侧留白 54-74px

## 根本原因

### 核心问题：ttf-parser hmtx ≠ Skia HarfBuzz 整形后宽度

**技术背景**：
1. **Rust 排版引擎**用 `ttf-parser` 的 `glyph_hor_advance`（hmtx 表原始 advance）测量字符宽度
2. **Skia 渲染引擎**用 HarfBuzz 整形后的 advance（经过连字、kerning、GSUB/GPOS、CJK 标点宽度类）
3. **两者存在系统性差异**：
   - 中文标点：`,` (半角) vs `，` (全角) 宽度差异 ~30%
   - 连字：`fi`、`fl` 在某些字体中会合并为单个 glyph
   - Kerning pairs：`AV`、`To`、`Yo` 等字符对有紧排调整
   - 上下文替换：阿拉伯文、印地文等复杂文字
   - 全角/半角数字：`０１２３` vs `0123`

**后果**：
- Rust 用 ttf-parser 估算断行位置（例如 21 个字符）
- Skia 实际渲染时宽度不同（可能只有 360px 而非 378px）
- 右侧留白 = `content_width - actual_rendered_width`
- 左右不对称 = `right_margin > left_margin`

### 三阶段修复路径

#### M10-B：创建 MeasureCache 架构（2026-09-01）

**设计方案**：
- Dart 端用 `TextPainter.layout(maxWidth: ∞)` 测量**真实渲染宽度**
- 批量回传给 Rust `MEASURE_CACHE`（FFI: `feed_text_widths`）
- Rust layout 二分搜索时优先查 cache，命中时用 Skia 真实宽度

**实现细节**：
- `rust/crates/layout_engine/src/measure_cache.rs`（170 行）
  - LRU 50,000 条
  - Key: `(font_name: String, font_size_bits: u32, text_hash: u64)`
  - `text_hash` 走 `DefaultHasher`（SipHash，跨进程可复现）
  - `font_size_bits` 走 `f32::to_bits()`（处理 NaN 边界）
  
- `lib/core/services/measure_text_service.dart`（202 行）
  - `configure(fontFamily, fontSize)` 同步配置
  - `measure(text)` 单次测量（返回 Skia 宽度）
  - `flushToRust()` 批量回传（调 FFI `feed_text_widths`）
  - LRU 50,000 条与 Rust 对齐

- 3 个 FFI 函数（`bridge/src/api.rs`）：
  - `feed_text_widths(book_id, widths_json)` - 批量喂入
  - `clear_measure_cache(book_id)` - 字体切换时清空
  - `get_measure_cache_stats(book_id)` - 调试用统计

**M10-B 实测结果**：❌ 无效（cache 命中率 0%）

**根因诊断**（explore-5/explore-6）：
1. `TextLine.width` 字段硬编码 `content_width`（4 处：lib.rs:341/627/670/715）
   - `emit_line!` 宏丢弃了 `measure_text_width()` 返回的实测宽度
   - 绘制端拿到的 `entry.width` 恒等于容器宽，无法反映实际排版宽度
   
2. MeasureCache 字体名 key 错配：
   - Dart 端：`MeasureTextService.configure(fontFamily: ReaderFont.family)` = **'ReaderSerif'**
   - Rust 端：`self.config.font_name` 默认值 = **'default'**
   - Cache key 包含 `font_name`，两者不一致 → 查询永远 miss

#### M12：Cache 命中率优化（0% → 95%+）（2026-09-02）

**M12 必修 1：measure_text_width 加 font_size 参数**

**问题**：标题行字号（25.2）与正文（18）不同，但 cache key 只包含 `self.config.font_size`（固定 18）
→ 标题行查询时 key 错误 → cache miss

**修复**：
```rust
// lib.rs:1180 - 签名改动
pub fn measure_text_width(&self, text: &str, font_size: f32) -> f32

// lib.rs:1227/1232 - 传播链路
get_char_width_inner(&self, ch: char, font_size: f32)
font_manager.measure_char(&self.config.font_name, ch, font_size)  // 关键！
```

**副作用修复**：
- ❌ Bug：lib.rs:1232 `get_char_width_inner` 内 `font_manager.measure_char` 仍用 `self.config.font_size`
  → cache key 用传入值，但实际测量用 18 → **cache key 与测量结果脱钩**
- ✅ 修复：改为 `font_manager.measure_char(&self.config.font_name, ch, font_size)`

**M12 必修 2：feedPageTextsWithPrefixes API**

**根本问题**（explore-6 锁定）：
- Dart `MeasureTextService.measure(text)` 喂入**完整 line text**（1 次/行）
- Rust `find_longest_fit` 二分查 `text[..mid]` **前缀子串**（log2(N) 次/行）
- **两者 key 集合数学上不相交** → 命中率 ≈ 1/N

**例证**：
- Dart feed: `"这是一个测试句子"` (9 字符)
- Rust 二分查询:
  - 第 1 次：`"这是一个测"` (5 字符) → miss
  - 第 2 次：`"这是一个测试句"` (7 字符) → miss
  - 第 3 次：`"这是一个测试"` (6 字符) → miss
- **只有完整 9 字符的查询才能命中**

**修复**：
```dart
// measure_text_service.dart:102-114
Future<void> feedPageTextsWithPrefixes(List<String> texts) async {
  for (final text in texts) {
    int i = 1;
    while (i <= text.length) {
      // 跳过 low surrogate（0xDC00-0xDFFF）
      if (i < text.length && 
          text.codeUnitAt(i) >= 0xDC00 && 
          text.codeUnitAt(i) <= 0xDFFF) {
        i++;
        continue;
      }
      final prefix = text.substring(0, i);
      await measure(prefix);  // 喂入所有 char-boundary prefix
      i++;
    }
  }
  await flushToRust();
}
```

**调用点**：
```dart
// reader_page_widget.dart:317
unawaited(MeasureTextService.instance.feedPageTextsWithPrefixes(
  pageTexts.map((e) => e.text).toList(),
));
```

**字符边界对齐**（M12-v2）：
- ❌ 错误：Dart `text.characters`（grapheme clusters）vs Rust `text[..mid]`（UTF-8 char boundary）
  - 对中文：单字符 = 单 code point → 一致
  - 对英文/标点：`"e\u0301"` (组合音标) = 1 grapheme vs 2 code points → 不一致
- ✅ 正确：Dart `text.substring(0, i)` + 跳过 surrogate pair
  → 与 Rust UTF-8 char boundary 在 **Unicode scalar value** 层面对齐

**M12 必修 3：Cache miss fallback**

**位置**：`emit_line!` 宏内（TXT）+ EPUB 3 处 TextLine 构造
```rust
width: measure_text_width(&line_text).min(content_width),
```

**目的**：ttf-parser 高估时，不会超过 content_width（容器宽）

**M12 实测结果**：✅ 完全解决
- 命中率：~95%+（feedPageTextsWithPrefixes 预热后）
- `rustW ≈ skiaW`（偏差 ≤ 1px）
- 左右边距精准对称（left=20px, right≈20px）

### M12-v3 错误方向（已证伪）

**假设**：epsilon 扣除导致断行提前
```rust
// lib.rs:1090 - 错误假设
if w <= max_width - eps {  // 改前
if w <= max_width + eps {  // M12-v3 尝试
```

**证伪依据**（M12-v4 调试日志）：
- 显示 Rust **同时**收到 `max_width=289.0`（错误）和 `max_width=394.0`（正确）双值
- 289 ≈ 434 × 2/3，epsilon (1-2px) 无法解释 289 vs 394 (105px) 的差距
- **真正根因是 Dart 侧传入参数错误，而非 Rust 侧算法问题**

**教训**：在修改算法前应先验证传入参数——添加调试日志输出参数是诊断第一步

### M12-v4 调试日志优化（最终验证）

**问题**：调试日志刷屏，无法截取精准信息

**优化**：
- 两个 FFI 入口（`get_page_structured` / `get_page_processed`）各自用 `AtomicBool` 守卫
- 仅首次输出：`[M12-v4] ... FIRST CALL: width=..., content_width=...`
- `layout_styled_paragraph` 前 3 次输出（避免刷屏）
- 移除 `break_line` 调试日志

- `rustW ≈ skiaW`（偏差 0px）
- `rightEdge` ≈ 398-414px（期望 414 = 394 + 20）
- 左右边距对称（left=20px, right=16-36px，视行长而定）

## 预防措施

### 1. 架构原则固化

已写入 `docs/design/ARCHITECTURE.md`：
- §5.2 缓存体系：L6 MEASURE_CACHE 层
- §11 模块速查表：layout_engine 添加 MeasureCache 职责
- §13 路线图：A18 MeasureCache 架构与左右边距修复

### 2. FFI 缓存协议规范

**通用教训**：任何 FFI 边界 + 持久缓存的组合都有隐含陷阱——
**调用方与被调方对 cache key 协议的约定是否一致**

**对账清单**（未来类似问题必含）：
- Dart 端 cache 增长曲线（`MeasureTextService.cacheLength`）
- `flushToRust()` 调用次数 vs 返回值累加
- Rust 端 cache 增长曲线（`MEASURE_CACHE.len()`）
- Rust layout 命中次数 vs miss 次数

### 3. 字符边界处理规范

**已知陷阱**：
- ❌ Dart `text.characters`（grapheme clusters）
- ❌ Rust `text.chars()`（Unicode scalar values）
- ✅ Dart `text.substring(0, i)` + 跳过 surrogate pair
- ✅ Rust `text[..mid]` + `is_char_boundary()` 检查

**规范**：跨语言字符串切分必须显式约定边界单位（byte / code unit / code point / grapheme cluster）

## 教训与启示

### 1. 分阶段修复的价值

**M10-B → M11 → M12** 三阶段渐进式修复：
- M10-B：建立基础设施（虽然未立即生效，但为后续打好地基）
- M11：修复显而易见的 bug（width 语义 + fontName 错配）
- M12：优化命中率（从部分生效到完全解决）

**如果一次性修复**：
- 问题复杂度 ×3
- 调试难度 ×10
- 容易遗漏细节（如 surrogate pair、font_size 传播链路）

### 2. 对账日志的重要性

**M10-B 实施时未做对账** → cache 命中率 0% 但未察觉 → M11 才发现

**正确做法**：
1. 实施新功能时必须包含"验证功能是否真正生效"的对账日志
2. 三方数据对比（Dart 写入量 vs Rust 查询量 vs 实际命中率）
3. 数学关系验证（feed N 条 → query N 次 → hit N - ε 次）

### 3. 字符编码的复杂性

**Unicode 的多层抽象**：
- Bytes（UTF-8/UTF-16 编码单位）
- Code units（Dart String 底层表示）
- Code points / Scalar values（Rust char）
- Grapheme clusters（用户感知的字符）

**跨语言协作必须显式约定边界单位**，否则"对中文一致、对英文不一致"的隐蔽 bug

### 4. 构建流程的陷阱

**关联问题**：`docs/bugfixes/2026-09-02_M12阶段调试日志导致DLL未更新.md`

**根因**：修改 Rust 后直接 `cargo build`，未复制 DLL 到 Flutter 加载路径

**解决**：始终使用 `fix_sync.ps1`（或手动复制 DLL）

**验证**：用户报告"添加调试日志后问题消失" = DLL 终于更新了
